## 2. 개념 아키텍처 — 교육용 Mermaid

```mermaid
flowchart TD
 A["변경할 코드"] --> B["브랜치·커밋·병합"]
 B --> C["검증된 변경 이력"]
 C --> D["예외·검증·학습 평가"]
```

**주의:** 개념의 관계를 보여주는 **설명용 그림**입니다. 실제 시스템 설계는 03단계, 구현은 별도 승인 이후 04단계입니다.

## 5. 한글·영어·공식 약어와 설명·재현 확인

**처음 등장:** 한글명(English Full Name, 공식 약어). 널리 쓰이는 약어가 **없으면 임의로 만들지 않습니다.**

| 한글명 | 영어 원명 | 공식·통용 약어 | 입문자를 위한 한 줄 설명 |
|---|---|---|---|
| **저장소** | Repository | 없음 | 버전 관리 대상 파일·이력 보관 |
| **브랜치** | Branch | 없음 | 개발 이력이 이어지는 이름 붙은 참조 |
| **커밋** | Commit | 없음 | 변경 상태를 기록하는 이력 단위 |
| **풀 리퀘스트** | Pull Request | PR | 변경내용 검토·병합을 제안하는 협업 방식 |

**자기 설명(Explain):** 커밋(Commit)은 작업 상태를 Git 이력으로 기록합니다. 커밋과 다른 브랜치로의 병합(Merge)은 별개의 과정입니다.

**종이 재현(Reconstruct, 실행 전 예상)**
1. 수정 전/후 파일 차이를 확인하는 상황 가정.
2. 변경 내용을 커밋으로 기록한다고 가정.
3. 커밋 식별 및 후속 검토가 필요함을 설명.

**오류·오해 예방:** 커밋을 만들었다고 바로 main에 병합되거나 GitHub에 자동 업로드되는 것은 아닙니다.

**확인 질문:** 책을 덮고 핵심 용어를 자기 말로 말할 수 있는가? 위 입력→처리→예상 결과를 종이에 다시 그릴 수 있는가?

**판정 주의:** 종이 재현과 기대 결과는 교육용이고, 코드 구현·실행·학습자의 독립 숙달 L4~L5는 아직 NOT_VERIFIED 또는 NOT_STARTED입니다. [00단계 시작으로 돌아가기](README.md).
